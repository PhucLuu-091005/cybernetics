# Direction B: Remove Escalations, Show Notes, Fix the Snags

Date: 15 October 2026. Status: draft for owner review. The owner chose direction B from `docs/design/2026-10-15-huong-cai-thien.html` (tropicbird worktree) on 15 October: "hướng B đi bạn". The snag ids (V1 to V23) come from the user guide `docs/design/2026-10-15-huong-dan-su-dung.html`.

## 1. Goal

The contest asks for "a tool to consolidate and organize context around a project, and give a clear picture of what has happened every step along the way". Escalations answer a different question, and the owner said they are not necessary. Direction B removes them, keeps the AI work in a simpler form (notes with cited steps), and fixes the snags that block a first-time user on the screens that stay.

Success:

1. The sidebar shows Graph and Review only. No screen, API route, MCP tool, scope, table or test mentions escalations.
2. The Graph opens on the whole project, with a cited summary note above it.
3. A click on a loop in the loop list opens its panel.
4. A closed loop never shows as broken.
5. Settings tells the user, in plain words, whether their agent connected.
6. Activity shows no git words and no console error.

## 2. Constraints and decisions

- **Base.** Branch `phucluu/direction-b` starts from `phucluu/zoom-out` (8d6187a, local), which sits on PR #15 (`phucluu/simplify-ui`). The zoom-out commit already makes "Fit the project" readable (icons at a fixed screen size, hover cards), so V2 needs no more work.

### 3.2 Migration

New migration `0002_remove_escalations.sql`, generated by `drizzle-kit generate` from the schema change, plus one hand-written statement:

1. `DROP TABLE escalation_analyses; DROP TABLE escalations;` (generated).
2. `UPDATE agent_tokens SET scopes = array_remove(scopes, 'escalations:write');` Stored tokens must still parse after the enum loses the value.

Section 7 adds a second migration, `0003_token_last_call.sql`.

A token whose only scope was `escalations:write` ends with no scopes. It still authenticates and every tool refuses it with "Scope <scope> is required". The token list shows it with "No permissions"; the user revokes it.

## 4. Notes (the AI work after Escalations)

The snapshot already holds `annotations: { id, text, actIds }`. Agents propose them through `update_proposal` with `graph:propose`, and a person approves them like any change. No screen shows them today. The UI calls them **notes**.

### 4.1 Text format

A note may cite a step inline with `[act:<lowercase uuid>]`. The UI shows each marker as a numbered link (1, 2, 3 …) in reading order. A marker whose act is not in `actIds` is invalid: `update_proposal` rejects it with a field error on `text`, the same rule the escalation answers used. A note without markers lists its `actIds` as numbered links after the text.

### 4.2 Where notes show

- **Graph, above the coverage line:** a "Notes" card. It shows the newest note (last in the array) clamped to 3 lines, a "Show all notes (n)" toggle, and the label "Interpretation, not evidence". The card is absent when the view has no notes.
- **Loop panel:** a "Notes" section lists every note that cites a step of this loop.
- A click on a numbered link opens that loop's panel at that step (`selectLoop(loopId, actId)`). If the step is after the As-of time, the link is grey with the tooltip "Not yet at this date".
- A change set shows its own notes, so a reviewer reads an agent's note before approving it.

### 4.3 Seed

The fixture history gets a fourth step after the undo: a merge "Summarise where the project stands on 9 October" that adds one note with 5 cited steps. The text is the example from the proposal page: go-live moved to 15 October, the silent sync report, the secret renewal and the side-letter mapping that wait on the client. Every date and name in it matches the engine output for the fixtures.

In `story-source.json` a note cites a step as `{act:<fixture key>}`. The builder turns it into `[act:<uuid>]` and fails when the key is not in the note's `acts`. The seed rekeys the markers together with the ids. Main then holds two notes; the summary is the newest, so the Graph card shows it first.

### 4.4 Agent recipe

`docs/mcp-agent-recipe.md` gets section "3b. Write a summary note": read the graph with `get_graph`, write one note with `[act:<id>]` markers, put it in a change set, and let a person approve it. The `update_proposal` tool description names the marker rule.

## 5. Graph fixes

### 5.1 V1: the first view

The first view is "Fit the project" (the floating control's action), not 100 % at T. After zoom-out, Fit shows all 36 loops, the milestones on the trunk and the red problems in one screen. A user then hovers for a card or clicks a step. SRD 7.2 changes its "first view" line to match.

This differs from the "after" image on the proposal page (81 % around T). That image showed about 10 days; Fit shows 5 months.

### 5.2 V3: loop list and panel

- A click on a loop name in the loop list selects the loop: the panel opens and the canvas zooms to the loop.
- While a panel is open, the loop list hides. When the panel closes, the list comes back if it was open before. The stored open or closed choice of the list does not change. One exception: the list button, pressed while a panel is open, closes the panel and shows the list; if the stored choice was closed, it becomes open.
- The "Show only" button on each row keeps its job.

### 5.3 V10: past problems

A problem on a loop that is closed, declined or cancelled is a **past problem**: it happened, and the loop ended after it.

| Place | Today | After |
|---|---|---|
| Loop colour (list dot, panel) | red | the end colour: green for closed, grey for declined or cancelled |
| Problem tag (list, panel) | "✕ Broken: Late delivery" | grey "Past: Late delivery" |
| Coverage line | "✕ 6 broken" | "✕ 4 broken" (current only), then "2 finished loops had a problem earlier." |
| "Problems only" | all loops with a problem | unchanged: past problems stay in, because they are part of what went wrong |

The branch on the canvas does not change: its segments already show red where the loop was late and green where it closed.

The proposal page drew "Closed, late" in orange. This spec uses grey, because orange already means "warning" and "due soon" (V13).

## 7. Settings fixes (V7, V20)

- V7 ends with section 3: the default scopes are every scope except "approve without you".
- Scope rows use plain titles, with the code in small grey text for matching agent errors:

| Code | Title | Text |
|---|---|---|
| `project:read` | Read the project | Records, the graph, notes and activity. |
| `records:import` | Add records | Paste or import messages. The graph does not change. |
| `graph:propose` | Suggest changes | Change sets wait for a person to approve them. |
| `graph:merge` | Approve without you | The agent can approve and undo changes. Grant it only to an agent that you direct. |

- "Connect your agent" loses "Streamable HTTP with a bearer token". It says: "Paste this into your agent's MCP settings. Replace inv_... with the secret of your token."
- **Connection check.** Migration `0003_token_last_call.sql` adds `agent_tokens.last_used_at timestamptz`. The server sets it when a call authenticates with the token, at most once a minute per token. The token list gets a "Last call" column: "Never" or a time such as "15 Oct 23:10", and a "Check again" button that reloads the list. The new-secret card says: "Ask your agent to list its tools. Then press Check again: Last call shows the time of that call." This checks the real agent, not the browser.
