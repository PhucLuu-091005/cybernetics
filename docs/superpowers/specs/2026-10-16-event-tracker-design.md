# Event tracker with change requests: design

- Date: 2026-10-16. Deadline: 2026-10-19 23:59 Asia/Ho_Chi_Minh.
- Branch: `phucluu/event-tracker`, from `phucluu/direction-b` (= `origin/main` 8b4e3a0 + 56 commits). Local only until the owner checks.
- Visual and behavioral reference: `docs/design/2026-10-16-event-tracker-v8.html`. It is a working prototype. When this spec is silent, copy the prototype. Its script holds the reference logic: `OPS`, `replayOps`, `keysOf`, `sameOp`, `clashesOf`, `liveOps`, `itemStatus`, `msStatus`, `graphSVG`, `layout`, `hiddenSet`, the review screen (`renderReview`), and the drag and drop code.
- Codebase facts: `docs/superpowers/specs/2026-10-16-event-tracker-codebase-map.md`.

## 1. Goal

Promise Graph becomes an event tracker for a whole project. It shows what happened at every step, which work led to which work across teams, and why plans changed. People or their agents add events and work items to a Queue, then drag them onto the graph. Main is read-only. Every change goes through a change request that a person with the Merge right merges (decision 20).

## 2. Product decisions (binding)

1. Event kinds (owner ruling 18 Oct, S1, E2 and T1, from `docs/design/2026-10-18-event-kinds-options.html`): Idea, Message, Issue, Task, Meeting, Decision, Delivery, Handoff, Done, Cancelled. No promise semantics.
   - Finish (E2): a work item finishes at its last visible finishing event: a Done, a Cancelled, or a Handoff marked "This finishes the work item" (`finishes: true`). Its finish time is the time of that event. A later visible event after it does not reopen the item; hiding the finishing event reopens it. A Handoff stores `finishes` only when it is true, so a Handoff of older data does not finish its item. A finishing Done or Handoff gives the Done statuses (decision 7). A Cancelled event ends the item as Cancelled and needs a written reason (its text, not empty after trim). A Handoff, finishing or not, still makes its source count as handed over (decision 3, Handoff mark).
   - Kind picker (T1): every kind picker (the Add an event and Add to the queue modals and the kind pop) groups the kinds under small uppercase labels: Start (Idea, Message, Issue), Progress (Task, Meeting, Decision, Delivery) and Finish (Handoff, Done, Cancelled). The groups are guidance only; any kind can sit anywhere. For a Handoff the picker shows the check box "This finishes the work item": checked for a new Handoff, the stored value in the kind pop; a kind change to Handoff leaves it unchecked. The kind pop stays open after a pick of Handoff and after a tick, so the box shows at once; another pick closes it. A kind change right after a kind change of the same event replaces it in the change request (one change per decision), and a change back to the first kind drops both. The schemas keep `finishes` only as `true` on a Handoff and drop it everywhere else, so `finishes: false` and no flag are the same change and never clash. Change descriptions, Queue cards, the event quote of Add this event and New work item, the event pop and the event list of the details say "Handoff, finishes the work item" (or "Handoff by <name>, finishes the work item").
   - Cancelled source: a cancelled work item hands nothing over, even when it had a Handoff before the cancel. Its handoff mark sits after the cancel in the neutral grey and says "Cancelled · <work item> no longer gets it from here"; with several receivers the list starts with "Cancelled, no longer hands over to". A receiver without events says "<source> was cancelled" (after "Waiting for …" when another source is still open), and its line never starts at the cancel.
   - Start hint (S1): there is no rule for the first event. When the first visible event of a work item is a Delivery, a Handoff or a Done, the Work item details show a quiet note under the status row: "This work item starts with a <Kind>. Add the event that started it, such as a Message, an Idea or a Task." Nowhere else: not on the graph, not in the review of a change request, not in lists.
2. One row per work item, under its team (lane), indented. A work item has an optional parent and zero or more "leads from" links (`after`). Inside a team, a child row comes right after its parent and its label is indented 12 units per level (3 levels at most). A parent in another team gives no indent: the details panel and the Focus show that link. The graph draws no vertical connector: no line from the milestone line to a work item, no line from a parent to its child, and no "leads from" curve.
3. Eye toggles hide a row or a whole team. A hidden row leaves no row, no line and no link on the graph. A hidden team takes no room and draws nothing, and so does a team whose rows are all hidden. A team with no work items in the window keeps its empty lane, because it is a drop target. The "N hidden" badge counts the hidden teams and the hidden work items. It shows only while something is hidden, as the last control at the right end of the context bar, on Main and in every change request view (owner, 18 Oct: it took the slot of the old "Open #N (draft)" button). A click on it opens a popup that lists them (name, and the team of a work item), each with Unhide, plus Unhide all; it closes on Esc and on a click outside. Unhide on a work item in a hidden team also shows that team. When Unhide removes the last hidden entry, the badge goes away and the focus moves to the control before it (the view selector on Main). A row whose own parent or own "leads from" source is hidden gets a small chip with the branch icon of the Graph rail item: its tooltip lists each hidden source as "From <title> (hidden)", and a click shows them again. Only direct children get the chip: a row that comes from the hidden source through a shown row (a grandchild) gets none. The graph draws no ghost line for a hidden source, and no line on the graph is dashed or dotted. Search and the links of the details panel show a hidden row again. Hide state is per viewer, kept in `localStorage`, never versioned.
   - Focus: each row has a focus button next to its eye. It shows only that work item and its descendants (children by parent and by "leads from", followed to the end), and every other row and every team without a shown row goes away. Each team head has the same button: a team focus shows the rows of that team and their descendants by the same rules (a team row that comes from another row of the team sits under it), and the Focus panel shows the team and its rows as a tree. The pressed focus button is a filled square in the `--focus` token, never a status colour. Hidden rows inside the focus stay hidden. While focused, a Focus panel on the right lists the parent of the focused item (a click focuses the parent instead) and the focused item with its descendants as a tree (a click scrolls to the row and flashes it, and shows it again when it is hidden). Focus on a hidden item shows it again. Leave focus in the panel, Esc, the focus button of the focused row (it is pressed while focused), or hiding the focused row or its team ends the focus, and so does a view where the item does not exist. A search pick or a details link to a row outside the focus ends the focus first. Focus is a view state only: it is not stored and does not change the hidden lists.
   - Handoff mark: a "leads from" link draws no line, inside one team or across teams. Each source row gets one mark for all the work items that lead from it. When the source has a visible Handoff event on the graph, the icon of its latest Handoff event (or of the stack that holds it) is the mark itself: one symbol, with no separate badge, and a small receiver count on its ring when there are several receivers. The source then counts as handed over. Without one, the mark sits after the finish, or after the T line while the source is open, and no other mark sits next to Done. Near the right edge the mark goes left of that point. The mark is a corner arrow that points up or down to the receivers, or a two-way arrow when they are on both sides, and it shows their count when there are several. A receiving item outside the window is not on the mark. Hover and keyboard focus show one line per receiver: "Handed over to <team> · received in <work item>" ("Hands over to <team> when done · …" while the source is open). With one receiver, a click, Enter or Space shows the receiving row again if it is hidden, outside the focus or filtered out, then zooms, scrolls to it and flashes it, as a search pick does. With several, the click opens a small list ("Handed over to", each receiver with its team); a pick does the same for that receiver, and Esc closes the list. On a Handoff icon, hover and focus also show the event line under the receivers. A stack that holds the Handoff event always opens the list, and the list ends with "Show the N events here", which opens the stack pop.
   - Row height (owner ruling 18 Oct, V1): the view menu at the left of the zoom bar (the rows icon, "Row height and teams") offers Comfortable (32-unit rows, the default since round 23, owner: "Row height mặc định nên là comfortable"), Compact (20) and Dense (12). At a lower level the row label, event circles and icons, deadline diamonds, handoff marks, chips, the + button and the eye and focus buttons get smaller, so nothing overlaps or is cut; every target keeps a hit area of at least 12 units. At Dense an event is a filled dot in its kind colour with no icon (hover, focus and click work as before), a stack still shows its circles behind, the waiting text moves to a tooltip, the Handoff icon drops its receiver count (the tooltip and the list keep the receivers), and the milestone name sits on the row centre only where the row has no line. The milestone circles on the pinned milestone line keep their size, as that band does not change height. The app keeps the level per person in `localStorage` (`promise-graph:row-height:v1:<user>`); without storage, or with an unknown value, the page starts at Comfortable.
   - Collapsible teams (owner ruling 18 Oct, V3): the head of each team is a summary row: a chevron, the team name and its count of shown work items, "N late · N not yet · N done · N cancelled" (only the counts above zero, late in the danger ink, done in the proceed ink and cancelled in `--ink-3`; nothing when all are zero). The summary row is 28 units high (24 at Dense) and the lane to its right stays empty: no bar and no event ticks (owner, 18 Oct, round 10). Every summary row is one line in the label column: chevron, NAME · N, then the focus and eye buttons at its right; a name too long for that line ends with an ellipsis before the buttons (`cutToWidth` in `layout.ts`: Geist advance widths, cut by grapheme on the NFC text with `Intl.Segmenter`, so a cut never splits a surrogate pair or drops a mark). The counts sit in the empty lane of the summary row, in `--fs-xs`, vertically centred, at the left edge of the visible time line: they stay there while the time line scrolls sideways (and on a phone, while the whole graph scrolls past the labels). The aria-label of the row keeps the counts (round 10 fix, controller ruling). Keyboard focus on the summary row shows a thin 1px `--ink-3` ring inside the row; a mouse click shows no ring, and hover shows the `--hover` fill only. A click, Enter or Space on the summary row opens or collapses the team (`aria-expanded`). A team with no shown work items has a plain summary row: no chevron, no button and no toggle. A collapsed team shows its summary row only, and its rows take no room. Every team starts open (round 23, owner: "expand all"). A collapsed team that holds a change shows its name with the yellow highlighter of decision 8; the person's own toggle wins and stays per project in `localStorage` (`promise-graph:team-open:v1:<project>`). Expand all and Collapse all sit in the view menu. Esc closes the view menu wherever the focus is, and so does a press outside it. While search text, filters or a focus narrow the graph, every team with a shown row is open; a toggle made then lasts until the graph is whole again, and the stored toggles come back. Anything that targets a row inside a collapsed team opens that team first; on a narrowed graph that opening is temporary and stores nothing, while an action that also clears the narrowing (a search pick that clears the only filter, a link that clears the filters or ends the focus) stores it, so the row stays in sight: a search pick, a handoff mark or its list, the links of the details panel (Parent, Leads from, Leads to), a member name in the milestone drawer, View in work item, the Focus panel, a branch chip and Unhide. Every change that targets a work item opens its team: placing, making or moving a work item into a team, adding or attaching an event to it, moving an event to it, and the field changes of the details panel. A handoff mark keeps its receivers in a collapsed team and names their team; a branch chip says "(in <team>, collapsed)" for a source there.
   - Filters: the search box has a filter control with Status (the 6 statuses of a work item, Cancelled included), Team, Milestone (and "No milestone") and Person (done by or requested by). Values of one kind combine with "or", kinds combine with "and". The typed search text also filters the rows with the same matcher as the result list (title, team and people, case and Vietnamese marks ignored), so the graph and the list show the same hits. A matching row keeps its parents, up to the top, as dimmed context; a team without a shown row goes away, and so does an empty team. Filters combine with hiding and the focus, add no chip for a filtered-out source, and are a view state only (not stored). A chosen team, milestone or person that the current view does not have (for example a team that exists only in a change request, after a switch to Main) does not filter and does not count. The control shows the count of chosen values, the panel shows "N of M work items match" and Clear filters. A search pick clears the typed text; a pick, a handoff mark or a details link to a row that the filters leave out clears the filters.
4. Queue: events and work items wait in a project Queue until someone drags them onto the graph. People add them with Add; agents add them through MCP. No email or Slack sync.
5. Drag and drop changes the graph only in a draft change request that the acting member edits. A Queue work item onto a team places it (onto a milestone circle sets its milestone while it waits); a Queue event onto a work item attaches it; a Queue event onto a team opens "New work item" from it; an event up or down moves it to another work item; anything onto the bin hides it (events) or removes it from the Queue (Queue cards). The bin shows only while something is dragged. The toast hides while something is dragged, so it never covers the bin. It stays in the accessibility tree, so a screen reader still announces it, and its timer stops; after the drop it shows again with its Undo for its full time, also when it came during the drag (round 16). A work item name onto a milestone circle adds it to that milestone. Every drop has a click alternative (pops and modals). Events sit at their real time in every view (owner ruling 17 Oct, round 7): there is no drag inside the day and no Reset position, and a read-only view starts no drag at all. Events closer than 16 units stack as before, the earlier ones under the later top event. The table `tracker_event_offsets` stays in the database with its old rows, but no route, payload field or screen uses it (round 7 review).
6. Milestones have 5 statuses: Planned, Finished early, Finished on time, Late, Finished late. A milestone is done when all its work items that are not cancelled are done; its finish is the latest finish of those work items. A cancelled work item never holds its milestone back and never makes it late. When every work item of the milestone is cancelled, the latest cancel is its finish, and the same rules give the status (round 10B choice). The deadline of a milestone is its planned date plus an optional time of day (`HH:mm`, project time zone). Without a time, the deadline is the end of that day. Late = not done and now is after the deadline. Finished late = the finish is after the deadline; Finished early = the finish day is before the planned day; otherwise Finished on time.
7. Each work item has a Planned finish: a date plus an optional time of day (`HH:mm`, project time zone), the same as a milestone deadline. Without a time it is the end of that day. Work items use the same 5 statuses against that instant, plus Cancelled (decision 1): Cancelled = the last finishing event is a Cancelled, whatever the dates; Late = not finished and now is after it; Finished late = the finish is after it; Finished early = the finish day is before the planned day; otherwise Finished on time. Add to queue (work item), Place work item, New work item from an event and the details panel take the optional time; Place keeps the time of the Queue card unless it sets a new date or time. Moving a Planned finish or a milestone date needs a written reason (not empty after trim). Every place that sets or moves a milestone date also takes the optional time: New milestone, the milestone drawer (Planned date and Time), Move the date, the drag of the milestone circle (it keeps the time), and the first milestone of New project (a time without a name and a date is refused, never dropped). A change of the time alone is a move. Labels and tooltips show the time only when it is set ("15 Oct 17:00"). The app keeps the first date and every move: who, when, from, to, why. The graph draws no date flag for a work item. The details panel shows the Planned finish and folds the first date and every move. In an editable change request, the Planned finish date and time in the details panel are inputs: a new value shows "Why does the date move? (required)" under them with Cancel and Move the date; a drag of the milestone circle opens the reason dialog with the dropped date.
8. Colours and marks:
   - A row is blue while open and green when done. The part of the line after the item's own Planned finish instant (its time when set, else the end of its day) is red while open and amber when done late. A cancelled row draws one neutral grey line (`--isolated`) from its start to the Cancelled event and nothing after it: never red, never amber.
   - Kinds colour the events, status colours the lines (owner ruling 18 Oct, K1). An event circle takes the colour of the event kind (`--k-*`; Task grey, Meeting brown) on all of it: a 2-unit ring at full strength, a light tint inside (12 % over `--panel` in light, 16 % in dark) and the icon (owner, 18 Oct: the light theme looked washed out); a stack takes the kind colour of its top (latest) event, and the circles behind it a stronger tint of that colour (26 % light, 30 % dark). The yellow change ring, the selection band and the focus ring stay as they are. The legend lists the 10 kinds, each drawn as its graph circle, and the Cancelled line colour next to the other line colours; its milestone statuses stay 5.
   - A milestone is a circle on the milestone line. Its fill is the status colour (Planned: an outline only). It shows a tick when finished early or on time, and "!" when late or finished late. Its label is "name · date · status" on 2 levels.
   - Milestones have no links and no chip column. Every member row shows a deadline diamond at the deadline (decision 6), and the milestone circle sits at the same point: at the time when it is set, else at the end of the day, after every event of that day.  The diamond is filled with the milestone status colour (Planned: an outline only), with a yellow stroke when a change request moved that date. It tells which milestone the row belongs to. The full milestone name shows once per team and milestone, beside the diamond of the first member row of that team: right of the diamond, or left of it when the right has no room, just above the line and inside the band of its own row. The T line, an event, a mark, a chip, a waiting text, the add button and the edge of the time line take room. When neither side has room for the full name, the name goes on the side with more room and ends with an ellipsis ("Go-live and fir…", at least 7 letters); with less room that team shows no name and no other row takes it. The milestone labels on the axis carry the panel colour behind them, so the T line and the grid pass behind the name. In an editable view, the "No events yet" or "Waiting for …" text of a row starts after the add button when the button would cover it. The same text starts after a handoff mark or a chip of its own row when the mark would cover it. Near the right edge it ends with an ellipsis instead, before or after the marks and the add button, on the side with more room; with less than 8 letters of room on both sides it moves left over the empty time line and ends before the first mark. It is never cut mid-word by the edge (round 16). A milestone date before the window start draws no diamond; the details panel still shows the milestone. Hover and keyboard focus show "<milestone name> · deadline <date> · <status>" (the date with its time when set), plus "This work item makes it late." or "This work item finished after it." when the row finished after the deadline, or is open while now is after the deadline or its Planned finish is after the milestone date. The overrun of the work item itself stays the red part of its line. A click, Enter or Space on the diamond opens the milestone drawer. A work item belongs to one milestone at most (round 24, part 12): New milestone lists only the work items with no milestone; replay refuses `msAdd` or a `newMs` member for a work item that is in another milestone ("<title> is in <milestone> already. Remove it from that milestone first."), so the server refuses it with that message; a drag of such a row onto another milestone says "<title> is in <milestone> already. Change its milestone in its details." and sends nothing. A move stays the explicit Milestone field of the work item details, which now sends `msRemove` and then `msAdd` in one write. While the milestone drawer is open (round 24, part 6), the graph lights the work items of that milestone the way Focus does: their row names turn bold and get the quiet selection band (`.hit.sel`, ink at 6 %, never a status colour), and every other row, its line, marks and name, dims (`.dim`). Closing the drawer ends it; a work item name in the drawer opens that item and scrolls to its row.
   - Yellow marks what a change request changed (owner choice C2): a highlighter behind a changed name (11 px), a solid 3 px yellow ring with a 30 % yellow fill around a changed event, and a 3 px yellow stroke on a changed milestone circle or a moved milestone date. The tokens are `--change` (light `#e0a800`, dark `#ffe629`), `--change-text` and `--change-bg` (light `#ffe14d`, dark `#6e5a00`); round 7 made them stronger so they read in both themes.
   - The picked row on the review graph and the reveal flash use a neutral band: a see-through light grey fill with a 1.5 px ink outline, so a yellow name inside them stays readable.
   - The row whose details are open gets a quiet see-through grey band made from the ink token (6 %), with no lines and no status colour, in both themes. A row with keyboard focus gets a thin 1 px outline in `--focus` above and below the row (no status colour). Scrolls that bring a row into view stop below the pinned axis (`scroll-padding-top` from the measured axis height, and the rail height on a phone). The review graph has no row buttons and no milestone buttons: its rows and diamonds show information only.
   - The T line is a solid thin grey line. No line on the graph is dashed or dotted.
9. No breakdown types and no day-count rules (no reply, accept, hedge or at-risk windows).
10. Projects: a signed-in user creates a project (client, project name, teams, optional first milestone with date). The New project dialog lists the default teams Product, Design, Engineering, QA and Operations as rows with a remove button (×), and an "Add a team" input where Enter (or Add) puts a typed team at the end; a name the list has is refused with "<Team> is already in the list.", and at least one team is required (round 7, owner request 17 Oct). The five defaults are the functions most delivery projects hand work between, so most projects only remove rows. Each project has one Main graph. The creator is the project lead. Teams are project settings (decision 20): the project lead adds, renames and deletes them on the Members page; a team can also come from a merged change request ("New team"). New team in a change request asks for the name only; the merged team starts with no lead and no people, because a team lead gets the create right and only the project lead may give rights (round 7 review).
11. Main is read-only, and so is every view that the acting member cannot edit: someone else's draft, a ready, merged or closed CR, and a person without the create right. Such a view has no drag and drop that changes the graph (only the sideways move of decision 5), no edit buttons in pops and drawers, and no "+" buttons; pops and drawers show the information only. On entering Main, a notice at the top says "Main is read-only. To change it, create a change request." with a close × and Don't show again (the top bar holds New change request); a person without the create right reads "Main is read-only. You can view it." instead, with no call to create (round 24, QA 19 Oct, L2) (kept per user in `localStorage`). The context bar of Main shows the view selector ("Main"), a read-only chip and the project lead with a small avatar ("Lead: Minh Trần"); Main has no second row with that sentence. In other read-only CR views, the context bar says what to do (Ask to edit, Ask for edit access, Edit again, Merge into Main); a person without the create right sees "View only." and no ask.
12. Change request (CR): statuses Draft, Ready, Merged, Closed. Numbered per project (#1, #2...). A CR view always shows the latest Main plus the CR's own changes. There is no Sync.
13. Share: the current editor adds people with Can edit or Can view. Everyone in the project can view every CR.
14. One editor at a time. The author edits first. A person with Can edit (or the author) presses Ask to edit; the current editor presses Hand over or Not now. The editor can also hand over without an ask (Share, Hand over). Asks wait; nothing moves editing automatically. A member without edit right (Can view, or no share) sees "View only." and an Ask for edit access button: it records the same ask, and the editor sees "<name> asks for edit access to #N." in the change request header with Grant Can edit (a Can edit share, which clears the ask) and Not now. To take over the editing after that, the person asks to edit.
15. Mark as ready locks the CR (needs at least 1 change that still applies; the server refuses a CR whose every change no longer applies). The current editor presses Edit again to unlock it (back to Draft).
16. Each change request has one page, `/projects/[id]/changes/[num]`, where people see, edit, review and merge it. The header is the context bar: the title is the view selector, then the status, the people, the editing state, the change count, the clash count, and the actions the person may take (Share, Cancel change request, Mark as ready, Edit again, Ask to edit, Ask for edit access, Request changes, Merge into Main). The left side panel lists the Changes (icon, item, change, before and after, the reason of a date move, who, a clash chip; a pick shades the row on the graph and scrolls to it; the editor has × on each change to undo it and Undo the last change). A change that needs an undone or missing earlier change says "no longer applies" with its reason. The change count in the header and on the Changes tab counts only the changes that still apply (`applying` of the review model), and these rows alone never enable Mark as ready. While such rows exist, a quiet line on top of the list says "N changes no longer apply." with a Clear button for the editor, which removes all of them, last first. Clear has no undo: a cleared change could not apply again anyway, as the change it needs is gone. A comment on a cleared change keeps its text but loses its link to the change, as with ×. If a removal fails part way (for example a 409), the rows that are left stay with their Clear button. A draft whose every change Main already has shows "0 changes", a disabled Mark as ready, "Every change is already in Main." in the header and the side panel, and Cancel change request to close it (`inMain` of the review model); for the editor it has a second tab, Queue, which holds the Queue (Add, Events and Work items, search, drag onto the graph). The graph on the right has Before (Main before the change request, read-only) and After (the change request, with yellow change marks); Before is read-only for everyone, and its side panel shows the Changes only, with no × and no Undo; the editor edits on After exactly as on the old CR view: drag from the Queue, add an event, mark done, move a date, rename, milestones and teams. A click on a row opens the work item details panel (the O1 panel of the `Drawers` section), which the editor edits in place there. A person who may merge sees the clash picks at the top of the Changes list on a Ready CR, and Request changes (a modal with a note, back to Draft) and Merge into Main (enabled once every clash has a pick) in the header. While the merger looks at a Ready CR, a newer revision waits behind "This change request changed since you opened it. Review again". A member with no View Main right gets "You cannot see Main of this project yet." on this page too. The page has no Conversation tab and no comment boxes; the comments stay in the data and the `comment` action stays in the API. Main has its own page, `/projects/[id]/graph`, read-only; an old link `/graph?cr=N` redirects to the change request page, and an old `?tab=` on the change request page is ignored. Cancel change request: the author, the current editor, or a person who may merge cancels an open (Draft or Ready) change request in a modal that needs a reason. The change request becomes Closed; its header says "Cancelled by <name>, <time>. Nothing went into Main." with "Reason: <text>", and History lists it under "Cancelled" with the reason. One label, "Cancel change request", serves every person, the merger included, so one action never has two names; the status chip stays "Closed".
17. Clash: a CR change clashes when Main took a different change on the same spot after the CR change was made. Spots (keys): queue event placement `event:<id>`, queue item placement `item:<id>`, event `act:<id>`, work item `loop:<id>:title`, `loop:<id>:ms`, `loop:<id>:due`, milestone `ms:<id>:date`, `ms:<id>:name`. Two different fields of one work item never clash. An identical change already in Main is dropped silently. The person who merges picks Main or the CR for every clash before Merge; the merge records each pick (label, kept value, dropped value, source CR number, who). Many clashes (round 24, part 11): the clash box in the side panel keeps its head in sight (sticky) with "N of M picked", Keep Main for all, Keep this change request for all (a clash whose change request side cannot apply keeps Main) and "Next to pick: <label>", which scrolls to the first clash with no pick and focuses its first choice; the clashes scroll in their own list (at most 480 px or 55 % of the window). Each clash heading is a button that shows its spot on the graph: a work item row scrolls into view with the reveal band, a milestone opens its drawer. While a clash has no pick, the bar says "Pick a version for <label>" before Merge into Main, and the Merge tooltip names it too (`pickAll`, `pickedCount`, `firstUnpicked`, `clashSpot` in `src/tracker/review.ts`).

## 3. Architecture

### 3.1 Approach

Build the tracker as a new vertical slice, then delete the promise subsystems. Port the prototype logic to TypeScript instead of adapting the promise engine, React Flow layout or proposal pipeline.

- `src/tracker/`: shared pure code, used by server and browser. No React, no Node APIs, no I/O.
- `src/server/tracker/`: database tables access, permissions, use cases, seed.
- `src/app/api/v1/projects/[projectId]/tracker/**`: REST routes through the existing `route()` and `domain()` helpers.
- `src/components/tracker/`: React UI. `src/app/(app)/projects/[id]/graph/page.tsx` renders Main; `src/app/(app)/projects/[id]/changes/[num]/page.tsx` renders the change request page with the same `TrackerScreen` and its `num`.
- A CR is an ordered list of operations (option B of the codebase map). Main is a base snapshot plus the operations of every merge, replayed in order. The browser replays with the same pure code, so views need no server round trip.

### 3.2 Pure model (`src/tracker/model.ts`)

Dates are `YYYY-MM-DD` strings in the project time zone. A milestone time and a planned finish time are `HH:mm` strings on the same clock; milestones, work items, Queue work items and their moves carry one, and stored data without it stays valid (the base, the queue and the ops are JSON, so the time needed no migration). `deadlineMs`, `milestoneDeadline`, `itemDeadline` and `formatDeadline` live in `src/tracker/deadline.ts`. A wall time that a daylight saving gap skips resolves to after the gap (`wallTimeInstant`), and a day whose midnight the clock skips (America/Santiago on 2026-09-06) starts at the end of the gap (`startOfDayInstant`). Instants are ISO 8601 strings with offset. Ids are UUID strings made by the client inside operation arguments, so a replay is deterministic.

```ts
type EventKind = 'message'|'task'|'handoff'|'decision'|'meeting'|'delivery'|'issue'|'done'|'idea'|'cancelled';
type Person = { id: string; name: string };                       // people in the story (event authors, Done by, For) and every project member
type Team = { id: string; name: string; leadId: string | null };   // lead = default Done by for a new item
type DateMove = { from: string; fromTime?: string; to: string; toTime?: string; why: string; by: string /* member id */; at: string };
type Milestone = { id: string; name: string; planned: string; plannedTime?: string; firstPlanned: string; firstPlannedTime?: string; moves: DateMove[] };
type WorkItem = { id: string; title: string; teamId: string; doneBy: string; requestedBy: string;
  milestoneId: string | null; parentId: string | null; after: string[];
  plannedFinish: string; plannedFinishTime?: string; firstPlannedFinish: string; firstPlannedFinishTime?: string;
  moves: DateMove[]; since: string | null };
type TrackerEvent = { id: string; workItemId: string; kind: EventKind; at: string; by: string; text: string;
  finishes?: boolean; // a Handoff only: true makes it finish its work item
  addedBy: string | null; hidden: boolean };
type QueueEvent = { id: string; kind: EventKind; at: string; by: string; text: string; finishes?: boolean; addedBy: string | null; agent: boolean; createdAt: string };
type QueueItem = { id: string; title: string; note: string; doneBy: string; requestedBy: string; milestoneId: string | null;
  after: string | null; plannedFinish: string; plannedFinishTime?: string; addedBy: string | null; agent: boolean; createdAt: string };
type TrackerState = { people: Person[]; teams: Team[]; milestones: Milestone[]; workItems: WorkItem[];
  events: TrackerEvent[]; queue: { events: QueueEvent[]; items: QueueItem[] } };
```

Zod schemas for all of these live in `src/tracker/schemas.ts` and validate every write.

### 3.3 Operations (`src/tracker/ops.ts`)

`type Op = { op: OpName; a: Record<string, unknown>; rev: number; by: string; agent?: true; via?: string; d?: OpDescription }` where `rev` is the Main revision the editor saw when making the change, `by` is the member id, and `d` is the stored description (item, change, before, after, icon, why).

Operations (prototype names): `attach {eventId, workItemId}`, `place {itemId, teamId, plannedFinish?, plannedFinishTime?}` (the time is read only with a date; without a date the card keeps its own), `qms {itemId, milestoneId}`, `fromEvent {id, eventId, teamId, title, doneBy, requestedBy, after, plannedFinish, plannedFinishTime?}`, `addEvent {workItemId, ev}`, `move {eventId, to}`, `kind {eventId, kind, finishes?}` (the flag is kept only for a Handoff; the clash key stays `act:<eventId>`), `hide {eventId}`, `msDate {milestoneId, date, time?, why, by, at}` (no time clears the old one), `msName {milestoneId, name}`, `msRemove {workItemId}`, `msAdd {workItemId, milestoneId}`, `newMs {id, name, planned, time?, members}`, `rename {workItemId, title}`, `due {workItemId, date, time?, why, by, at}` (no time clears the old one), `addTeam {id, name, leadId}`, and the field changes of the details panel (round 7): `doneBy {workItemId, personId}`, `requestedBy {workItemId, personId}`, `team {workItemId, teamId}`, `parent {workItemId, parentId | null}` (never the item itself), `after {workItemId, after[]}` (each once, never the item itself). Parents and sources together never form a loop: an op whose new parent or new source reaches the item again through parents and sources fails ("this link would make a loop of parents and sources"). The append refuses it; the review marks it "With the links Main has now, it would make a loop of parents and sources." and Merge stays off; the server refuses the merge with CONFLICT, so the editor removes the change or the merger requests changes. Their clash keys are `loop:<id>:doneBy`, `requestedBy`, `team`, `parent` and `after`.

Pure functions:

- `applyOp(state, op): { state, entry }` throws `OpError` when the op does not fit (a queue entry is gone, an id is unknown, a reason is empty).
- `replayOps(base, ops): { state, entries, marks }`: skipped ops become entries with `skipped: true`; `marks` lists ids changed by the ops (rows, events, milestones, dates) for the yellow change marks.
- `keysOf(op)`, `sameOp(x, y)` (compares `op` and `a` only; a date move compares the target, the date and, for a milestone, the time). A change of only the time of a milestone or a planned finish uses the date key (`ms:<id>:date`, `loop:<id>:due`), so it clashes like a date move.
- `clashesOf(crOps, commits)`: for each CR op, look at the Main ops merged after `op.rev`; drop it when an identical op exists; report a clash when a key matches: `{ key, index, x, y, commit }` (latest matching Main op wins).
- `liveOps(crOps, commits, picks?)`: CR ops minus identical ones, minus ops whose clash was picked `main`.
- `mainState(base, queue, commits, upto?)` and `crState(base, queue, commits, cr)`: CR view = Main at the latest revision plus `liveOps`; a merged CR shows Main right after its merge; a closed CR shows Main at its close revision plus its ops.
- `describe(op, state)`: plain words for lists and diff cards; `diffLines(op)` gives the before and after lines; `clashLabel(clash, state)`.

The queue in the state: `initial = base + all queue rows that are not dismissed`. Ops consume queue entries by id. A queue row added after a merge is still in the initial list, so replays stay valid.

### 3.4 Status and layout (`src/tracker/status.ts`, `src/tracker/layout.ts`)

- `itemStatus(item, events, asOf, timeZone)` and `milestoneStatus(milestone, items, events, asOf, timeZone)` return `planned | early | ontime | late | flate` (and `cancelled` for a work item, decision 1) with the prototype rules in the project time zone. A work item compares the finish and `asOf` with its planned finish instant (`itemDeadline`). A milestone compares the finish and `asOf` with its deadline instant (decision 6): its time when set, else the end of the planned day, which gives the same result as a calendar day compare. The Late chip of a milestone and of a work item in their drawers says how late they are, so the word shows once: "Late by N h" on the day of the deadline, else "Late by N days" ("Late by 1 day"), never "0 days" (`lateBadge` in `src/tracker/deadline.ts`). The Planned finish row then shows only the date, in red.
- `layoutTracker(state, view, marks?)` returns a render model: lanes, rows (with `depth` for the indent and `dimmed` for filter context), line segments with colours, event groups (icons stacked when closer than 16 units, with every id), milestone circles with 2 label levels (a label tries, in order: above the axis on its usual side, below it, then the other side; a spot is free when no label on its line is within 8 units and, below the axis, no other milestone marker is within 12 units of it, so a moved milestone's marker never covers the next label, QA L2 round 23; round 24, QA 19 Oct, M1: labels never overlap at any width or count, as a label with no free spot gets shorter first, dropping the status, then the date, then cutting the name with "…", and with no room at all it shows no text, while its accessible name keeps the whole label; the deadline order and the reverse order both run and the one that shortens less wins), deadline diamonds on member rows (`deadlines`), ↖ chips for hidden sources (`chips`), trunk segments, one handoff mark per source row (`handoffs`, each with its `targets`), the T line and the axis ticks. It draws no stems and no curves. A row with a hidden parent or source gets a chip; a parent or source outside the focus or the filters gets none. `view = { hiddenRows, hiddenTeams, asOf, timeZone, span, dayWidth, fitSpan, zoom, windowStart, focus, focusTeam, filter, density, collapsedTeams, plusButtons }`; each lane carries `head`, `collapsed` and a `summary` (counts, bar, ticks, label), and the layout returns its `level`. `collapsedTeams` and `lateTeams` (`src/tracker/teams.ts`) give the default rule of decision 3, where `filter` is the `{ match, context }` that `matchRows` (`src/tracker/filter.ts`) gives. `focusTree`, `descendantsOf`, `teamFocusTree` and `teamDescendants` (`src/tracker/focus.ts`) give the focus trees and their ids. An event is drawn at its own time. Default window: the screens pass `windowStartFor(state, project.windowStart, asOf, timeZone)`: the project start, moved back to 3 days before the earliest start of a work item on the board (its first visible event, or the start of an empty item) when that is earlier, so every event shows at Fit; work items that finished before the project start stay off the board. Without a project start the layout takes 3 days before the earliest relevant start. The window ends at the later of `asOf + 7 days` and the latest planned date + 3 days. A weekly tick never sits on the first day, where the label column would cut its date.
- Geometry: one unit is one CSS pixel, so sizes, fonts and icons never follow the width of the board. A fixed label column of 228 units (`SIDE`), indent 12, and the row level of the view (`density`, `ROW_LEVELS`): row 32, 20 or 12 with a team summary row of 28, 28 or 24. The view gives `span` (the measured width of the visible time line), and `dayWidth` (units per day, 2 to 480; the floor drops to the fit when a long window fits under 2, so Fit always fits, see `clampDayWidth`). Without `dayWidth`, the scale is `zoom` (1 to 12) times the fit of the window to `fitSpan`, the first measured width. A wider `span` keeps the scale and draws more of the time line after the window end (ticks, trunk and drop bands follow). The layout returns `dayWidth`, `fitDayWidth` (the fit to the current `span`) and `zoom` (their ratio). The time line scrolls on its own while the label column stays put. Everything above `TOP` (64: the axis, the T pill and the milestone line with its labels) is drawn in its own pinned band. The axis picks the shortest step whose gap holds a date label (64 units, the width of "28 Sept" with room on each side): every day, every week (Mondays), every two weeks, the first of every month, or every three months, so two labels never touch at any zoom (round 7 review).

### 3.6 Members, acting member and permissions (`src/tracker/permissions.ts`, `src/server/tracker/access.ts`)

- The project creator gets a member linked to their user id; it is the project lead (`owner_member_id`, `project.leadMemberId` in the payload).
- Access: a person opens a project through its workspace or through a member row of their own that is not removed; a removed member row closes the project, also to a person of its workspace (`projectOpenTo` in `src/server/db/tx.ts`, also in the identity store and the project list). Agent tokens follow the same rule.
- Acting member: in a demo project, the cookie `pg_act_<projectId>` names a member of that project, and only a member of the project's workspace may set it; otherwise the member linked to the session user. A present member acts (`Member.active`: not removed and not a pending invite); what they may do comes from the rule below. With no member, the person reads as a workspace reader.
- The rule (pure, shared by the browser and the server; `tests/unit/tracker/permissions.test.ts`):
  - `GRANTS = ['viewMain', 'viewCrs', 'createCrs', 'mergeCrs']`, `Grants = Record<Grant, boolean>`, `NO_GRANTS`, `DEFAULT_GRANTS` (an invite), `ALL_GRANTS`, `GRANT_LABEL`.
  - `closeGrants(grants)` adds what each grant needs; `setGrant(grants, grant, on)` turns on what it needs, or turns off what needs it; `impliedBy(grants, grant)` names the grants that hold it on.
  - `rightsOf(subject): Rights` with `Rights = { viewMain, viewCrs, create, merge, manage }` and `subject = { me: { id, grants } | null, project: { leadMemberId }, base: { teams: [{ leadId }] } }` (a `TrackerPayload` fits). The project lead has every right; a team lead gets `create`; no member reads Main and the change requests only. `memberRights({ projectLead, teamLead, grants })` gives the same for one member.
  - `can(payload, right)` with `right` one of `viewMain`, `viewCrs`, `create`, `edit`, `merge`, `manage` (`edit` without a change request is `create`), and `can(payload, crRight, cr)` for one open change request: `edit` (a draft whose current editor you are, with `create`), `share` (its current editor, with `create`), `ask` (`create`, not its current editor), `cancel` (its author, its current editor or `merge`). The UI asks every such question through it, and the server checks the same rules.
  - `canSeeCr(payload, cr)`: the `viewCrs` right, or View Main and the change request is merged or the person has a part or a share in it. `mergerIds(payload)`: the present members who may merge, the project lead first (the UI names them: "Minh Trần or Quang Nguyễn merges it").
- Server enforcement (inside the transaction): `requireRight(ctx, scope, right)` (people, and agents whose token holds a scope that uses that right), `requireQueueWriter(scope)` (agents too), `requireView(scope)` (every payload; FORBIDDEN with `details.reason = 'no-view'`), `rightsIn(scope, member)` for another member. The payload filters the change requests with `canSeeCr`. Round 24 (QA 19 Oct, L1): a member who opens Main but lacks View change requests and opens `/changes/<num>` that is not in their payload sees "You cannot view change requests in this project." (the project lead decides; a link to the Members page names the lead) with Back to Main, for every number, so the page tells nothing about which change requests exist; a person with the right gets Page not found for a number that does not exist.
  - create CR, ask to edit: `create`; comment: a change request the person can see; add to the Queue, dismiss a Queue card: `create` (agents: the rights of the token user's member).
  - add op, undo, remove op, share, mark ready, edit again: the CR's current editor (who has `create`), and the status allows it (draft for ops and ready; ready for edit again).
  - ask: a member with `create` who is not the current editor, on an open CR; without edit right (author or share `edit`) it is an ask for access. A `share` that gives Can edit clears that member's ask. Cancel ask: the asker; hand over: the editor, to a member with `create` and edit right; share `edit`: only to a member with `create` (the Share modal offers Can edit only to them); not now: the editor.
  - merge, request changes: `merge`; merge needs status `ready` and a pick for every clash; the server recomputes clashes and rejects stale picks.
  - close (Cancel change request): the author, the current editor or a member with `merge`, on a Draft or Ready CR, with a reason of 1 to 1000 characters; the reason is the body of the `closed` comment.
  - act as: only in demo projects, only for a person of the project's workspace, and only as an active seeded member (no user) or as their own member, never as an invited person.
  - list the members and teams: anyone who opens the project. Invite, grants, hand over the lead, remove, add/rename/delete a team, team people and lead: `manage` (the project lead, `src/server/tracker/members.ts`).
  - sign-in: an invite whose email matches the signed-in email becomes that person's member. If the person has a removed member in that project, that member comes back with the grants, teams and team leads of the invite, and the invite goes away.
  - return link (QA 18 Oct, L7): a signed-out person who opens a page of the app goes to `/signin?next=<path>` and lands on that path after the sign-in (local or Google; Google keeps it in the `pg_oauth_next` flow cookie). The proxy hands every request its own path in the `x-pg-return-path` header, because a layout cannot see the page path. `returnPath` (`src/server/http/return-path.ts`) accepts only a same-origin relative path of a page: it refuses a scheme, `//`, a backslash, white space or control characters, the home page, `/signin`, `/api`, `/mcp` and `/_next`; anything else lands on the home page. Sign out goes to plain `/signin`. In demo mode the return link goes to `/api/auth/demo?next=<path>` instead (item 19, Demo mode).

`TrackerPayload = { project: {id, title, clientName, timeZone, windowStart, asOf, demo, leadMemberId}, members: Member[], me: Member | null, canActAs: boolean, base, queue: {events, items}, commits: Commit[], crs: Cr[] }` where `Cr` holds ops, shares, asks and comments, `Member.active` says that the member is present (not removed, not a pending invite), and `Member.grants` holds the grants. `TrackerPayload` also carries `version`. New changes (round 22, owner request 19 Oct, GitHub pull request style): the screen never changes by itself because of a write it did not make (another person, another tab or an agent): not Main, not the Queue, not a change request, not the change request list or its counts, not the comments, not the members. A light check runs while the page is visible: `GET /tracker/version` every 5 minutes (round 23, part 12, owner: no frequent polling), at once when the tab shows again, and at once when the window gets the focus back after 1 minute or more away (the same check, no second timer); a hidden tab sends nothing. It answers `{ version, crCount }` (`TrackerVersion` in `src/tracker/version.ts`); on a change request page the check sends `?num=<n>` and the answer also has `cr: { num, revision, updatedAt }` of that change request (null when the viewer cannot see it). The version is four short hashes joined with dots, one per part (`VERSION_PARTS`): `main` (the last commit and the commit count), `queue` (the cards that are not dismissed, with an md5 of each payload), `crs` (number, title, author, editor, status, revision, updated time, shares, asks and the comment count and last comment of each change request the viewer may see) and `project` (project facts, the tracker row with its teams, the members, the acting member and `canActAs`). `versionOf` in `src/server/tracker/version.ts` reads only ids, revisions and counts (no ops, no comment bodies), and `buildPayload` uses the same function, so a payload and a check of the same data give the same version. A read never changes it; a change request the viewer cannot see never changes it for that viewer. The check has its own rate limit bucket (`poll`, 60 a minute for each person since round 23; it was 600 for the 15-second check), apart from the 300 reads. When the check finds a newer version, the context bar shows one quiet line on the right, after the spacer: "<what> · Refresh" in `--ink-2` with a link-style Refresh button, no card and no colour. <what> is "Main changed" when Main changed, "This change request changed" when the change request on screen has another revision or updated time (an ask, a share or a comment moves only the time), "N new change requests" when only the change requests changed and their count grew, "Change requests changed" when only they changed, "The Queue changed" when only the Queue changed, else "New changes" (`freshLabel` in `src/components/tracker/fresh.ts`). The context bar holds it because it shows on Main and on every change request page, it describes the data of the view, and it sits above the graph without covering it; the top bar holds search and the global buttons and wraps on a phone. Full view hides the context bar and so the notice too. Refresh reads `GET /tracker` and puts the payload in place: no page reload, the scroll, the zoom, the filters and an open drawer stay (a drawer whose item is gone shows nothing); on a change request page the merger keeps the version they opened and their clash picks, as a pull request keeps a review: when the revision of that change request moved, the bar says "This change request changed since you opened it." with Review again, and Merge waits; when it did not move, the picks stay. The Refresh button is off while a write runs, and a Refresh whose answer comes back after an own write is dropped, so it never rolls that write back. A drawer whose item is gone after Refresh closes. A browser reload shows the new data too. The person's own writes return the new payload with its version, so they show at once and never raise the notice; a check that overlaps a write in flight is dropped. Writes run one after another (each waits for the reply before it), so two quick drops send the revision of the reply before them and both land. A write that fails with 409 (the data moved on) keeps the screen as it was and shows the error in the toast with a Refresh button, and the check runs at once so the notice shows too. One exception: an append (a drop, an added event, any edit of the draft) that gets a 409 reads the payload again and retries once when the draft on the server only gained changes after the ones on screen, with the same status and editor (`onlyAppended`), as when the editor's own agent appends through MCP; the server checks the change against the latest data again, and the reply shows both. Every other 409 offers Refresh. The hour clock that moves T keeps running. MCP and the other API calls do not change.

### 3.9 MCP (`src/server/mcp/tools.ts`)

Scopes (owner ruling 18 Oct, round 14: one scope per right, each with a checkbox, no "everything" scope). `src/contracts/scopes.ts` (`SCOPE_INFO`) gives each scope a group, a title, a short name, one line of what the agent can then do, and the right of the creator it needs:

| Group | Scope | Title | Needs |
|---|---|---|---|
| Read | `project:read` | Read the project | View Main |
| Queue | `queue:add` | Add to the Queue | Create |
| Queue | `queue:dismiss` | Remove Queue cards | Create |
| Change requests | `crs:edit` | Edit change requests (open, add and remove changes, share, hand over, ask to edit, decline an ask) | Create |
| Change requests | `crs:ready` | Mark ready (and back to draft) | Create |
| Change requests | `crs:comment` | Comment | View Main (a member) |
| Change requests | `crs:merge` | Merge into Main (and request changes) | Merge |

| People and teams | `members:manage` | Manage members (invite, grants, remove) | Manage (project lead) |
| People and teams | `teams:manage` | Manage teams (a team lead gets the Create right) | Manage (project lead) |

- No scope manages tokens (create, list, revoke), deletes the project or hands over the project lead (review ruling: an agent could invite an outsider and make them lead), and no tool does it; the token service refuses every agent actor and `updateMember` refuses an agent lead hand-over. The page shows "The agent can invite people and give them rights." under People and teams. A stored token that still holds `project:lead` reads without it (`knownScopes`).
- Creation checks the scopes against the creator's rights today (`createTokenService(store, creatorOf)`): a scope the creator cannot give answers VALIDATION with the reason the page shows ("You do not have the Merge right in this project"). A token without scopes gets the default scopes (`project:read`, `queue:add`) that the creator may give. Every scope but `project:read` needs a member.
- At each call the server checks both: the tool's scope is in the token (`requireScope`, message `Scope <scope> is required`), and the creator's member holds the right today (`requireRight`, with the member rows read in the same transaction). The token stores no copy of the rights, so a creator who loses a right, or leaves the project, takes it from the token at once. `requireRight` also refuses an agent whose token has no scope that uses the right, so a new caller of a use case cannot skip the scopes.
- A key is its creator's key (owner ruling 18 Oct, round 17: "agent đóng vai như người tạo agent luôn, coi nó như một cái key của user"). Everything an agent writes with it shows as its creator, exactly as if the person did it in the browser: `add_queue_event` without `by` names the creator's member (as the Add dialog does), and change requests, changes, comments and History name that member. The internal marks stay for audit only: a Queue card has `agent`, a change request op has `agent: true` and `via` (the key label), and a change request comment has `by_agent` and `via_key`. The app never shows an agent as an author: no Agent chip on a Queue card, no "Agent" name and no "AI" avatar; the change list of a change request shows a small "via key <label>" after the name of the person on a change that a key added. `get_change_request` shows `agent` and `viaKey` on each change and comment.
- Two kinds of key (`agent_tokens.kind`, round 17). A project key (created in project Settings) works only in its project, and its tools take no `projectId`. A personal key (created on the Profile page) has no project (`project_id` null) and works in every project its person can open, now and later, with that person's live rights in each project: each tool call names `projectId`, and the MCP adapter binds the key to that project with the rule of a page (`projectOpenTo`), so a removal from one project stops the key there at once and a removal everywhere stops it everywhere. A right is offered at creation when the person holds it in at least one project (`personalCreator`; the reasons read "in any of your projects"), and the server checks the right in the project of each call. `list_projects` (no scope, personal keys only) gives the person's projects with id and name. A personal key lists `list_projects` and every tool with a required `projectId`; a project key keeps its listing, and `list_projects` answers NOT_FOUND for it. The server instructions differ by kind (`INSTRUCTIONS`, `PERSONAL_INSTRUCTIONS`). Rate limits stay per key (60 calls a minute). REST for personal keys: `GET` and `POST /api/v1/me/keys`, `DELETE /api/v1/me/keys/<id>`; a key never manages keys, deletes a project or hands over a lead.

Tools (one per web action of the HTTP API, each tied to one scope; every write reuses the use case of its route): `project:read`: `get_project`, `get_tracker`, `list_queue`, `list_change_requests`, `get_change_request`, `list_members`. `queue:add`: `add_queue_event`, `add_queue_item`. `queue:dismiss`: `remove_queue_card`. `crs:edit`: `create_change_request`, `add_change`, `remove_change`, `hand_over_change_request`, `share_change_request`, `ask_to_edit`, `cancel_ask_to_edit`, `decline_ask_to_edit`. `crs:ready`: `mark_ready`, `mark_draft`. `crs:comment`: `comment_change_request`. `crs:merge`: `merge_change_request`, `request_changes`. `crs:close`: `cancel_change_request`. `members:manage`: `invite_member`, `set_member_grants`, `remove_member`. `teams:manage`: `add_team`, `update_team`, `delete_team`. Every token lists every tool; a tool outside the scopes answers `FORBIDDEN`. Inputs are strict: for a project key `projectId` and `actAs` fail with `VALIDATION`; a personal key needs `projectId` and refuses `actAs`. A change request write answers the change request summary (number, title, status, author, editor, change count, revision), never the whole payload. `list_members` answers `canManage` and `canManageTeams` for the token: its person's lead right today and the matching scope. `get_tracker` keeps teams, work items with status, `plannedFinish`, `plannedFinishTime`, `firstPlannedFinish` and `firstPlannedFinishTime`, milestones with status, `planned`, `plannedTime`, `firstPlanned` and `firstPlannedTime` (a time is `HH:mm` or null), and the open CRs. ### 3.12 Deploy (round 15: Google Cloud Run and Neon, owner's choice over Render)

The `Dockerfile` builds the standalone server. The container runs `scripts/migrate.mjs`, then `server.js`, which listens on `PORT` (8080 by default; Cloud Run sets it). `scripts/healthcheck.mjs` (the Docker `HEALTHCHECK`) calls `/api/health` on the same `PORT`; on Cloud Run a startup probe calls `/api/health`. `/api/health` never touches the database, so a probe never keeps Neon awake. The migration step uses `MIGRATE_DATABASE_URL` when set, else `DATABASE_URL`; it refuses a Neon pooled (`-pooler`) host, takes a session advisory lock (`hashtextextended('promise-graph:migrations', 0)`, logging `migrations_waiting` while another start holds it) around the Drizzle migrate, and sets UTC as the role's default time zone. The app pool (`poolConfig` in `src/server/db/client.ts`) has at most 5 connections and a 10 s connection timeout for a Neon wake-up, and it sends the `TimeZone=UTC` startup option only to a direct host, as the Neon pooler refuses startup options. Cloud Run runs one instance at most (`--max-instances 1`), as the rate limits live in process memory, and none when idle. The limiter (`MemoryRateLimiter`) only answers allowed or refused, and each caller raises its own `RATE_LIMITED` error or busy page; `AppError` also matches a value with its `Symbol.for` brand and a string `code`, not by class identity; a subclass keeps the normal prototype check. So under `next dev`, which builds each route on its own while the limiter and the identity store live on `globalThis`, a limit answers 429 or `/welcome?reason=busy` as in production, never 500 (QA 19 Oct, L1). Every response, pages, API routes, `/mcp` and `/welcome` alike, carries `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin` (`headers()` in `next.config.ts`, QA 19 Oct, L2). Every path except the photo route also carries `Content-Security-Policy: frame-ancestors 'none'`: a config header replaces a route's header of the same name, so the photo route keeps its own `default-src 'none'; sandbox`. `scripts/deploy-cloud-run.sh` refuses to start while a value is missing or wrong. It creates a runtime service account (`<service>-runtime`) with no project role, stores the three secrets (four with `AUTH_MODE=google`, its default being `demo`) in Secret Manager through stdin, lets only that account read them, and runs one `gcloud run deploy --source . --service-account …` in `asia-southeast1`. With `UPDATE_SECRETS=1` it destroys the old secret versions only after the deploy works. It accepts `NEXT_PUBLIC_APP_URL` only when it is the status URL or one of the `run.googleapis.com/urls` of the service. The CI image job maps host port 3000 to the container port 8080. The steps live in `docs/deploy-cloud-run-neon.md`. `render.yaml` is gone.

Deploy from a tag (round 19): `.github/workflows/deploy.yml` runs on a pushed `v*` tag, or by hand from a tag with the input `tag`. It calls `ci.yml` (a `workflow_call`), so a failed check stops the deploy; `ci.yml` runs on branch pushes and pull requests, not on tag pushes. Only the deploy job gets `id-token: write`, and it runs in the environment `production`. One whole run goes at a time (workflow concurrency group `deploy`, no cancel), so an older tag never deploys after a newer one. It signs in with Workload Identity Federation (`vars.GCP_WIF_PROVIDER`, `vars.GCP_DEPLOYER_SA`; no secret, no key), builds the `Dockerfile` on the runner, pushes `asia-southeast1-docker.pkg.dev/promise-graph/promise-graph/app:<tag>` and `:<sha>`, and runs `gcloud run deploy promise-graph --image …:<tag>` with no env, secret or account flag, so the service keeps the config of the manual deploy. It waits until the newest revision is ready, runs the new image and serves all traffic, checks that `/api/health` returns `ok`, and writes the URL to the job summary. Every action in both workflows is pinned to a full commit SHA. `scripts/setup-github-cd.sh` runs once after the first manual deploy and refuses to start without the service and its runtime account. It creates the repository `promise-graph` (cleanup policy: keep the 3 newest images), the account `promise-graph-deployer` with `roles/run.developer` on the service, `roles/artifactregistry.writer` on the repository and `roles/iam.serviceAccountUser` on the runtime account, and the pool `github-actions` with the OIDC provider `github`. A second run creates nothing and sets the same condition again.

- Storage drivers behind `PhotoStore` (`put`, `get`, `remove`): `gcs` (production; `AVATAR_BUCKET`; the Cloud Storage JSON API through `fetch` with a token from the Cloud Run metadata server, which is how Application Default Credentials work there; no Google client library) and `local` (dev and tests; `AVATAR_DIR`, default `.avatars/`, git ignores it; refused when `NODE_ENV=production`). `AVATAR_STORE` picks the driver; without it photos are off (initials only, no Photo section; the Profile page stays for the personal keys). `src/instrumentation.ts` reads the config at server start and exits with code 1 when it is wrong (Next only logs an error thrown in the hook and keeps serving), so `AVATAR_STORE=gcs` without a bucket stops the start. `sharp` 0.35.5 is a direct dependency; the standalone output traces it with its prebuilt libvips, checked in `next build` and in the Docker image (linuxmusl) on 18 Oct.
